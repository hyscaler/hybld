## The problem hybld solves

A CMS-backed static site with N pages traditionally rebuilds all N pages on every deploy. At large N this is slow, hammers the CMS API into rate limits, and makes publishing one article cost a full rebuild. hybld makes builds proportional to what changed.

## The manifest

hybld's memory is a SQLite database (default `.hybld/manifest.db`) with one row per built page:

| Column | Purpose |
| -------- | --------- |
| route | The page's URL path (primary key). |
| page_type | Which `pages.*` config produced it. |
| article_id, slug | CMS identity for collection pages. |
| content_hash | Hash of the page's `data()` result; unchanged data means the page can skip. |
| cms_modified_at | The CMS modification timestamp. |
| asset_graph_hash | Which version of your app code rendered it (see code-staleness). |
| dependents_ref | The dependents computed at build time, so deletions can rebuild the right listings. |
| feed_ref | The page's RSS entry, captured at build time. |
| source_ref | For aggregate pages: the enumerated item and page number, so the page can be rebuilt without re-enumerating. |
| output_path | Where the HTML lives, relative to outDir. |

The manifest can be exported/imported as JSON, merged (parallel chunked builds), and pushed/pulled over HTTP (presigned S3 URLs work). See [CLI reference](/reference/cli/).

## Page types: collections and aggregates

**Collection pages** are adapter-backed: one page per CMS item. The page type named `article` is a collection by default; any other type opts in with `collection: true` and may carry its own adapter:

```ts
pages: {
  article: { route: ..., data: ..., dependents: ... },
  author: {
    collection: true,
    adapter: wordpress({ baseUrl: CMS, postType: "users" }),
    route: (u) => `/authors/${u.slug}/`,
    data: (u) => ({ name: u.name }),
  },
}
```

**Aggregate pages** derive from many items: the home page, category archives, a 404 page. Singletons declare just `route()` and `data(ctx)`; enumerated aggregates add `enumerate`, optional `paginate`/`pageCount`, and `data(item, page, ctx)`.

## URLs: the CMS address is never the frontend address

Every article has two unrelated addresses, and hybld never derives one from the other:

```
CMS (where content lives):        https://cms.example.com/2026/07/summer-sale/
Frontend (where the page serves): https://www.example.com/articles/summer-sale/
```

The frontend URL is generated by exactly one function, your collection's `route()`, from the article's **data**:

```ts
route: (a) => `/articles/${a.slug}/`
```

Everything downstream flows from it: the output file path (`dist/articles/summer-sale/index.html`), the sitemap entry, the feed link, the canonical URL, and the redirect map when a slug changes. Your URL scheme is entirely yours; the CMS's permalink structure is irrelevant. Date-based, category-based, or locale-prefixed schemes are all just different `route()` functions.

Identity travels between the CMS and hybld as **id or slug**, never as a URL. To build the page for one specific article:

```bash
hybld build --ids 123            # what a publish webhook gives you
hybld build --slugs summer-sale
```

The reverse mapping, frontend URL back to CMS identity, is the optional `match()` hook (the inverse of `route()`), which powers serve-mode regeneration on miss:

```ts
match: (route) => {
  const m = route.match(/^\/articles\/([^/]+)\/$/);
  return m ? { slug: m[1] } : null;
}
```

### CMS URLs inside your content

One place CMS addresses do leak into the frontend: the article body. WordPress-style HTML contains absolute links to the CMS domain, both media and internal links to other posts. Media is handled by the `images` config (downloads and rewrites automatically). Internal links are yours to rewrite in `data()`, which is exactly what it is for:

```ts
data: (a) => ({
  title: a.title.rendered,
  html: a.content.rendered.replaceAll(
    /https:\/\/cms\.example\.com\/\d{4}\/\d{2}\/([^\/"]+)\//g,
    "/articles/$1/"     // CMS permalink pattern -> your frontend route pattern
  ),
}),
```

Because `data()` output is hashed, changing this rewrite logic counts as a content change: affected pages rebuild on the next run.

## Build scopes

Every build has exactly one scope:

| Scope | Meaning |
| ------- | --------- |
| `--all` | Full catalog plus all aggregates. |
| `--limit N` | First N items per collection (smoke tests). |
| `--chunk i/n` | Deterministic slice of the catalog (ordered by collection then id), for spreading a full build across CI jobs. |
| `--chunk-size N` | The next N never-built pages. |
| `--routes/--slugs/--ids` | Explicit targets. `--ids author:5` targets a non-default collection. |
| `--since last-build` (or a date) | Everything the CMS reports as modified since then, plus deletions when the adapter supports them. |
| `--stale` | Pages rendered by an older version of your app code. |

## Content hashing and skipping

Every page's `data()` result is hashed. A page renders only when its hash changed, its output file is missing, its asset graph moved on, or `--force` is set. This makes builds idempotent: re-running any scope with nothing changed skips everything.

The contract that makes this sound: **everything a page renders must derive from its `data()` result**. Content fetched elsewhere (possible on Next/Astro, where pages can fetch anything) is invisible to hashing and can go stale until a forced rebuild.

## Dependents

Publishing, editing, or deleting an article affects more than its own page: the home listing, its category archive, the sitemap, the feed. The `dependents` function declares this:

```ts
dependents: (a) => ["/", { type: "category", id: a.category_slug, depth: 2 }],
```

String entries name singleton routes; object entries name enumerated aggregates, where `depth` bounds how many archive pages rebuild (default 3, tolerating staleness on deeper pages). Dependents are stored in the manifest at build time so a deletion can rebuild exactly the listings that referenced the deleted article.

## Code-staleness

Your app code and your content change independently. When code changes, previously built pages keep working against the old hashed assets (the assets directory is append-only), but their manifest rows no longer match the current asset graph hash. `hybld build --stale --chunk-size N` progressively re-renders them; `hybld assets gc` deletes asset files no page references anymore.

The asset graph hash is a hash of build artifacts for the react-vite backend, and a **source fingerprint** for delegated backends (Next emits differently-named runtime files every build, so hashing output would mark everything stale after every run).

## The two rendering strategies

**Owned (react-vite)**: the path for a **plain React app** built with Vite (no meta-framework). hybld runs the Vite client + SSR builds itself and renders each page by calling your entry-server module in a worker pool. Millisecond warm rebuilds; hybld controls the HTML template, head injection, and hydration payload. See the [React + Vite guide](/frameworks/react-vite/).

**Delegated (next, astro)**: hybld never renders. It writes the batch scope to `.hybld/scope.ndjson` (route, page type, identity, and prefetched data per line), runs the framework's own production build, and the framework's dynamic routes read the scope through helper packages (`hybldParams`, `hybldPaths`). hybld then merges the emitted pages and hashed assets into its cumulative outDir and runs all shared post-steps.

Delegated details worth knowing:

- Static framework routes (home, 404) rebuild on every framework run regardless; they merge back as "extras" and singleton page data is included in every scope file so those pages stay correct.
- Every batch includes at least one page per dynamic route type (padded from the manifest, or one live CMS item on a fresh manifest), because Next's export refuses an empty `generateStaticParams`.
- Each incremental run costs one framework build (seconds), the price of using stable framework contracts instead of reimplementing their renderers.
